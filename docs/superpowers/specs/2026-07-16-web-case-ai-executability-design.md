# Web Case AI Executability Design

## Goal

Make Web cases consistently editable, convertible to executable automation, and generated by AI under project-aware rules and explicit browser DSL contracts.

## Web Case Library

The conversion dialog derives projects, modules, selected scope, and count from the active case kind. Web conversion validates every candidate before persistence and reports the case ID plus reason for invalid cases. A row-level conversion command converts one Web case without changing the current filter.

The Web action column exposes reorder, edit, convert, and delete commands at a stable width. Editing uses the existing Web editor, preserves the saved case identity and order, reparses step text, and refuses malformed action lines instead of silently producing locator steps from prose.

## Project Rules

AI rules have two scopes: system defaults and project overrides. Effective rules are a field-level merge where a project-provided field replaces the corresponding system field. Every response includes system version, project version, and an effective version label. Existing system endpoints remain compatible; project-specific calls use `projectId`.

Requirement analysis and formal generation load effective rules for the current project. Call records store the effective rule version and Skill IDs.

## Skills

Two built-in Skills are registered:

- `requirement-test-point-analysis`: generates evidence-linked requirement test points and never pretends natural-language procedures are locators.
- `formal-web-case-generation`: converts confirmed Web test points into complete executable cases with page, start URL, browser, viewport, precondition, ordered DSL steps, assertions, and source traceability.

## Executability Contract

Supported Web DSL actions are `goto`, `click`, `input`, `select`, `hover`, `waitForVisible`, `waitForUrl`, `assertVisible`, `assertHidden`, `assertText`, `assertUrl`, and `screenshot`. `manual` is not accepted for executable AI output.

Each line must parse to a supported action and a valid target. Numbered prose, bare sentences, missing targets, unsupported actions, and selector-like natural language are rejected. At least one assertion action is required. Browser and viewport values are normalized to runner-supported values.

After the first LLM response, the backend validates every generated Web case. Invalid output triggers one structured repair request containing exact validation errors and the original output. If repaired output is still invalid, generation fails with actionable case-level errors and no malformed cases are returned.

## Verification

Tests cover active-kind conversion sources, one-row Web conversion, editor persistence, rule merge/version behavior, Skill registration, prompt rule injection, invalid DSL detection, one repair attempt, valid case mapping, and runner-compatible payload generation.
